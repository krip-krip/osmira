# Mesures — chaîne OsmiraCore → agent → ptzview sur Raspberry Pi 4 (2026-11-27)

Premier essai de bout en bout de la visualisation (étape 3 de la roadmap) :
OsmiraCore sur un PC Linux, agent + `ptzview` sur `panelTest`.

## Montage

- **Pi** : `panelTest`, Pi 4 1 Go, Trixie, FFmpeg `7.1.5 +rpt2`. Code copié par
  `git archive` de `main` (`b192846`), `ptzview` compilé sur le Pi avec
  `-Wall -Wextra -Werror` : aucun avertissement. `uv` 0.13.10 installé dans
  `~/.local/bin`, agent lancé avec `uv run osmiracam-agent -c agent.toml`.
- **Core** : PC Linux en Wi-Fi, `10.7.1.63`, même réseau local que le Pi
  (`eth0` `10.7.1.30`). `uvicorn --host 0.0.0.0 --port 8000`.
- **Vidéo** : 4 × AW-UE150 → MediaMTX `192.168.104.253` (chemins `cam1`–`cam4`),
  joint par le Pi via NetBird (`wt0`). SRT 20 ms, H.265 1080p50.
- **Core** : station `panelTest` (`max_decoders` 4, 1 sortie), 4 caméras,
  droits `decode` + `view` en positions 1–4.

## Résultats

### Démarrage
- Agent : config reçue du Core et flux SSE connecté en ~0,5 s.
- **Écran branché sur `HDMI-A-2`** (et non `HDMI-A-1` comme noté jusqu'ici) :
  avec `connector = HDMI-A-1`, `ptzview` s'arrête aussitôt (« connecteur
  introuvable ») et l'agent le relance toutes les 2 s, comme prévu.
  Corrigé par `connector = auto` (premier écran branché) : `HDMI-A-2 1920x1080@50`.
- 4 flux connectés et affichés en ~0,2 s après le lancement de `ptzview`.

### Flux
| Caméra | État | i/s | Débit | Erreurs de décodage |
|---|---|---|---|---|
| cam1 | streaming | 49,9 | 16,2 Mb/s | 0 |
| cam2 | streaming | 49,2 | 15,7 Mb/s | 0 |
| cam3 | streaming | 50,0 | 15,8 Mb/s | 0 |
| cam4 | streaming | 49,8 | 15,4 Mb/s | 0 |

- Pertes SRT ponctuelles (`RCV-DROPPED … delayed for 20–23 ms`) suivies de
  `frame_post_process: Decode fail` jusqu'à l'image clé suivante : même
  phénomène que la question ouverte « pertes SRT » / « latence 20 ou 40 ms ».
- Ressources : RAM disponible 446–462 Mo, **CMA libre 68–74 Mo** (contre
  94–120 Mo lors de la maquette : à suivre en endurance), 51–56 °C,
  `throttled=0x0`.

### Bascule depuis la matrice du Core
Commande `PUT /api/stations/panelTest/outputs/1/selection` envoyée **depuis le
Pi** (une seule horloge pour la mesure), 6 bascules :

| Mesure | Valeurs |
|---|---|
| Commande → nouvelle image à l'écran (total) | **105 à 164 ms** |
| dont `ptzview` (requête `/select/N` → image) | 32 à 52 ms |
| dont Core + SSE + agent (+ lancement de `curl`, Wi-Fi du PC) | ~70 à 110 ms |

Depuis le PC, 4 bascules : `ptzview` 20 à 33 ms après la requête.

### Changement de caméras à la volée
Retrait puis remise du droit de cam4 dans le Core :
- nouvelle config appliquée par l'agent aussitôt (événement `config_changed`) ;
- `ptzview` relancé, **0,37 s** entre la réception de la config et la
  première image, sur la caméra choisie dans la matrice (cam3).

### Core injoignable
- Core arrêté : les 4 flux continuent à 50 i/s, l'image reste ; l'agent
  l'écrit une fois (`cannot reach the Core`, `event stream lost`).
- Core relancé : reconnexion automatique, `state` resynchronise la caméra
  affichée ; bascule depuis la matrice de nouveau en 22,6 ms (`ptzview`).

## À retenir
- La chaîne de visualisation fonctionne de bout en bout sur le vrai matériel.
- Mettre `connector = "auto"` par défaut (fait dans `agent.toml.example`).
- Mesurer la bascule Core → Pi avec un Core filaire et avec un Core distant.
- Surveiller la CMA libre en endurance (68–74 Mo aujourd'hui).
